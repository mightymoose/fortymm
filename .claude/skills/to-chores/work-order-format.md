# Work-order format

The single source of truth for the `.claude/work-order.md` structure. `/to-chores`
writes it; `/do-chores` reads it. The **checkboxes are the run state** — a ticked
box means the implementing agent reported that chore done; `/do-chores` resumes
from them.

**One commit per chore, one PR per slice.** Each slice is a branch stacked on the
one before it, so its PR reviews only that slice's diff. The `Branch:` and `PR:`
lines under each slice heading are the stack's durable state — they are how a
resume in a fresh session finds the branches it already pushed and the PRs it
already opened, so they must be written the moment each is created, not at the end.

## Structure

```markdown
# Work order: <plan title>

Source: <path/URL to the plan, PRD, or issue — or "conversation">
Tickets: <comma-separated GitHub issue numbers this arc closes — e.g. `#933, #959` — or `—`>
Stack base: <the branch slice 1 stacks on — usually `main`>
Branch prefix: <the designated branch name; slice branches append `-s1`, `-s2`, …>
Generated by /to-chores. Drive with /do-chores. Checkboxes are the run state.

## Slice 1: <demoable outcome — a full sentence describing the visible result>

Branch: `claude/github-issue-933-ab12cd-s1` (stacked on `main`)
PR: —

- [ ] 1a `[api]` Add rating to the profile BFF response + schema
  - **Scope:** the profile BFF endpoint only; no rating *computation* changes.
  - **Depends on:** —
  - **Read first:** docs/adr/0007-rating-on-profile.md
- [ ] 1b `[main]` Regen OpenAPI types (schema.d.ts + Types.swift)
  - **Scope:** generated types only; no hand edits.
  - **Depends on:** 1a
- [ ] 1c `[web-client]` Render the rating on the profile page
  - **Scope:** profile page + its e2e page.route stubs.
  - **Depends on:** 1b
  - **Read first:** docs/adr/0007-rating-on-profile.md
- [ ] 1d `[ios]` Show the rating on the profile screen
  - **Scope:** profile screen only.
  - **Depends on:** 1b

## Slice 2: <demoable outcome>

Branch: `claude/github-issue-933-ab12cd-s2` (stacked on `…-s1`)
PR: —

- [ ] 2a `[web-client]` ...

## Testing notes

Scenarios a black-box tester must cover, in user-observable terms. `/qa-review`
receives these as **must-cover scenarios**, *in addition to* Quinn's own
adversarial exploration — they are a floor, never a ceiling.

- **Happy path:** a player with rated matches opens their profile → the rating shows.
- **Edge — empty:** a brand-new player opens their profile → "Unrated", not `0`, not blank.
- **Edge — boundary:** a player whose only rated match was voided → back to "Unrated".
- **Regression risk:** the match list still renders for players with no rating.
- **Not observable in the UI:** the per-user seed cutoff (covered by `pytest` in 2a only).
```

## Field rules

- **Tickets** (header) — the GitHub issue number(s) on the FortyMM project board
  (github.com/users/mightymoose/projects/8) this whole arc closes, comma-separated
  (`#933, #959`), or `—` when the work has no ticket. `/do-chores` moves each of
  these cards to **In Progress** when it starts driving; `/epic` moves them to
  **Done** once the arc's acceptance gate passes. Both call
  `scripts/project-status.sh`.
- **Stack base** (header) — the branch slice 1 stacks on, normally `main`. Every
  later slice stacks on its predecessor.
- **Branch prefix** (header) — the designated branch name for the arc. Slice
  branches are that name with `-s<N>` appended, so the whole stack is greppable and
  a resume can find it without guessing.
- **Branch** (per slice) — the slice's own branch, and what it stacks on. Written
  by `/do-chores` when it cuts the branch at the start of the slice. Until then,
  `/to-chores` writes the name it *will* have, so the plan is reviewable before any
  branch exists.
- **PR** (per slice) — `—` until `/do-chores` opens it, then the PR number
  (`#1234`). This is the field `/land-the-plane` reads to know what to gate and
  merge, and the field a resume reads to know a PR is already open rather than
  opening a duplicate.
- **Checkbox + ID** — `- [ ] <slice-number><letter>`. IDs are stable and unique;
  `depends-on` references them.
- **Agent tag** — one of the `name`s discovered from `.claude/agents/` (`[api]`,
  `[web-client]`, `[ios]`, `[infra]`, `[e2e]`), or `[main]` for a chore the driver
  does inline (regen, integration, glue). Exactly one tag per chore.
- **What to build** (the text after the tag) — behavior + surface, one line, no
  "and". **No hard file paths** — name the surface, not the file.
- **Scope** — one line on what the chore does *not* touch, to keep it single-tree
  and atomic.
- **Depends on** — comma-separated chore IDs that must be ticked first, or `—`.
- **Read first** (optional) — path(s) to the ADR / `CONTEXT.md` section carrying
  the decision this chore needs. Omit when there's nothing to read.

## Testing notes

A `## Testing notes` section at the **end of the work order**, covering the whole
plan. These are *black-box, user-observable* scenarios — what someone driving the
running app should be able to confirm. `/do-chores` ignores them; `/qa-review`
consumes them as **must-cover scenarios** on top of its own adversarial
exploration, and `/epic` checks them off at the end of the arc.

Group them so a tester can act on them:

- **Happy path** — the demoable outcome of each slice, stated as a user action.
- **Edge cases** — empty, boundary, duplicate, concurrent, back/reload mid-flow.
- **Regression risks** — surfaces the change could plausibly break in passing.
- **Not observable in the UI** — invariants only a unit/integration test can reach.
  List them explicitly so the QA pass doesn't waste effort hunting them, and so
  nobody mistakes "Quinn found nothing" for "this invariant holds".

Write them in the domain's language (see `CONTEXT.md`), never in file paths or
function names — the QA agent never reads the source.

## The stack

One commit per chore, one branch and one PR per slice, each slice stacked on the
one before it:

```
main ── s1 (PR #1) ── s2 (PR #2) ── s3 (PR #3)
         │             │             │
         1a 1b 1c      2a 2b         3a 3b 3c      ← one commit each
```

**Why the split is where it is.** A chore is single-tree and often meaningless on
its own — a bare OpenAPI regen, or an API schema with no consumer yet. It makes a
fine *commit* (an atomic, bisectable step) and a terrible *PR* (nothing to review,
nothing to demo). A slice is defined as a demoable increment, which is exactly what
a reviewer needs. So the commit boundary is the chore and the review boundary is
the slice.

**Merging is bottom-up**, one PR at a time, as each goes green — that is the point
of stacking. `/land-the-plane` owns it.

**Squash-merge rewrites history, so the stack must be rebased after every merge.**
The repo squash-merges. When `s1` squashes into `main`, `main` gains *one* new
commit whose SHA matches none of `s1`'s, while `s2` still carries `s1`'s original
commits. A plain rebase onto `main` then replays those already-merged commits and
conflicts against itself. The fix is to rebase `s2` **onto `main`, from `s1`'s old
tip** — dropping exactly the commits the squash absorbed:

```bash
OLD_BASE=$(git rev-parse s1)          # BEFORE deleting s1, capture its tip
git fetch origin main
git rebase --onto origin/main "$OLD_BASE" s2
git push --force-with-lease origin s2
```

Capture `OLD_BASE` **before** the merge deletes the branch — recovering it
afterwards means digging through the reflog. `--force-with-lease`, never `--force`:
the lease is what makes a concurrent push a refusal instead of a silent loss.

GitHub retargets an open PR's base automatically when its base branch is merged and
deleted, so `s2`'s PR re-points at `main` on its own. Verify it rather than assuming
it — the retarget is best-effort and does not fire in every case.

## Blocked chores

When `/do-chores` stops a slice on failure, it marks the failed chore so a resume
can see it — append `⚠ BLOCKED: <reason>` to the chore line and leave the box
unchecked:

```markdown
- [ ] 3b `[api]` ... ⚠ BLOCKED: pytest failing on the FK constraint, see run notes
```
