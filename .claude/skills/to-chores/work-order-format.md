# Work-order format

The single source of truth for the `.claude/work-order.md` structure. `/to-chores`
writes it; `/do-chores` reads it. The **checkboxes are the run state** — a ticked
box means that chore is done and verified; `/do-chores` resumes from them.

## Structure

```markdown
# Work order: <plan title>

Source: <path/URL to the plan, PRD, or issue — or "conversation">
Generated by /to-chores. Drive with /do-chores. Checkboxes are the run state.

## Slice 1: <demoable outcome — a full sentence you could verify by hand>

- [ ] 1a `[api]` Add rating to the profile BFF response + schema
  - **Scope:** the profile BFF endpoint only; no rating *computation* changes.
  - **Depends on:** —
  - **Read first:** docs/adr/0007-rating-on-profile.md
  - **Verify:** `pytest tests/test_profile.py`
  - **Proves:** the profile endpoint returns the player's current rating, and `null` for a player with no rated matches.
- [ ] 1b `[main]` Regen OpenAPI types (schema.d.ts + Types.swift)
  - **Scope:** generated types only; no hand edits.
  - **Depends on:** 1a
  - **Verify:** `mise run regen-api-types && mise run regen-ios-api-types` — no drift
  - **Proves:** the committed generated types match the live OpenAPI document.
- [ ] 1c `[web-client]` Render the rating on the profile page
  - **Scope:** profile page + its e2e page.route stubs.
  - **Depends on:** 1b
  - **Read first:** docs/adr/0007-rating-on-profile.md
  - **Verify:** `npm run test:run && npm run test:e2e`
  - **Proves:** a rated player's profile shows the number; an unrated player's shows "Unrated".
- [ ] 1d `[ios]` Show the rating on the profile screen
  - **Scope:** profile screen only.
  - **Depends on:** 1b
  - **Verify:** `xcodebuild build ... CODE_SIGNING_ALLOWED=NO`
  - **Proves:** the profile screen compiles against the regenerated types and renders the rating.

## Slice 2: <demoable outcome>

- [ ] 2a `[web-client]` ...

## Testing notes

Scenarios a black-box tester must cover, in user-observable terms. `/qa-review`
receives these as **must-cover scenarios**, *in addition to* Quinn's own
adversarial exploration — they are a floor, never a ceiling.

- **Happy path:** a player with rated matches opens their profile → the rating shows.
- **Edge — empty:** a brand-new player opens their profile → "Unrated", not `0`, not blank.
- **Edge — boundary:** a player whose only rated match was voided → back to "Unrated".
- **Regression risk:** the match list still renders for players with no rating.
- **Not observable in the UI:** the per-user seed cutoff (covered by `pytest` in 2a only).
```

## Field rules

- **Checkbox + ID** — `- [ ] <slice-number><letter>`. IDs are stable and unique;
  `depends-on` references them.
- **Agent tag** — one of the `name`s discovered from `.claude/agents/` (`[api]`,
  `[web-client]`, `[ios]`, `[infra]`, `[e2e]`), or `[main]` for a chore the driver
  does inline (regen, integration, glue). Exactly one tag per chore.
- **What to build** (the text after the tag) — behavior + surface, one line, no
  "and". **No hard file paths** — name the surface, not the file.
- **Scope** — one line on what the chore does *not* touch, to keep it single-tree
  and atomic.
- **Depends on** — comma-separated chore IDs that must be ticked first, or `—`.
- **Read first** (optional) — path(s) to the ADR / `CONTEXT.md` section carrying
  the decision this chore needs. Omit when there's nothing to read.
- **Verify** — the concrete command the implementing agent runs to prove the chore
  is done. Must be checkable, not a vibe.
- **Proves** — one line naming *the observable claim that command establishes*.
  Required. `Verify` is the command; `Proves` is what a green command means. A
  command can pass for the wrong reason (the test didn't exercise the new path, the
  suite was already green before the change) — `/do-chores` re-runs `Verify` itself
  and rejects the chore if the claim in `Proves` isn't actually established. Write it
  as a falsifiable sentence about behavior, not "tests pass".

## Testing notes

A `## Testing notes` section at the **end of the work order**, covering the whole
plan. These are *black-box, user-observable* scenarios — what someone driving the
running app should be able to confirm. `/do-chores` ignores them; `/qa-review`
consumes them as **must-cover scenarios** on top of its own adversarial
exploration, and `/epic` checks them off at the end of the arc.

Group them so a tester can act on them:

- **Happy path** — the demoable outcome of each slice, stated as a user action.
- **Edge cases** — empty, boundary, duplicate, concurrent, back/reload mid-flow.
- **Regression risks** — surfaces the change could plausibly break in passing.
- **Not observable in the UI** — invariants only a unit/integration test can reach.
  List them explicitly so the QA pass doesn't waste effort hunting them, and so
  nobody mistakes "Quinn found nothing" for "this invariant holds".

Write them in the domain's language (see `CONTEXT.md`), never in file paths or
function names — the QA agent never reads the source.

## Blocked chores

When `/do-chores` stops a slice on failure, it marks the failed chore so a resume
can see it — append `⚠ BLOCKED: <reason>` to the chore line and leave the box
unchecked:

```markdown
- [ ] 3b `[api]` ... ⚠ BLOCKED: pytest failing on the FK constraint, see run notes
```
