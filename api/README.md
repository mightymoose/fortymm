# api

fortymm's HTTP API: FastAPI on Python 3.15, with PostgreSQL 18 (the `api-db` service). Run everything through `./bin/mise run api:<task>`; `CLAUDE.md` lists the tasks.

## Layout

| Where | What goes there |
| --- | --- |
| `src/api/services/<concern>.py` | A service class that holds one piece of logic, plus the plain results it returns (frozen dataclasses). It returns results for expected outcomes instead of raising, and knows nothing about HTTP or the response format: no status codes, no FastAPI types, no `data` or `errors`. |
| `src/api/routes/<resource>.py` | A route gets its service from `api.dependencies`, calls it, and converts each result into a status code and a response document (below). Its response models (`<Resource>Document`, `<Resource>Resource`, `<Resource>Attributes`) live in the same file. No logic of its own. |
| `src/api/routes/errors.py` | The error document: `ErrorDocument`, `error_response()` for routes, and the handlers that give FastAPI's own errors the same shape. |
| `src/api/routes/v1.py` | The `/v1` router. A new route module joins it with `router.include_router(...)` and writes its paths without the prefix. `/openapi.json` and `/docs` stay unversioned: one document covers every version. |
| `src/api/dependencies.py` | FastAPI dependencies that build services from settings (and, later, the connection pool). |
| `src/api/app.py` | `create_app()`: reads settings from the environment at startup (`src/api/settings.py`; `DATABASE_URL`), installs the error handlers and includes the routers. |
| `openapi.json` | The API's contract, generated by `api:openapi`. CI fails when it is out of date, and when it would break clients of the base branch's copy (`api:openapi-breaking`, oasdiff). Response models appear in it under their class names. Their docstrings become schema descriptions. |
| `Dockerfile` | The production image. The dev image is `dev/api/`. |

## Responses and errors

Response bodies are shaped after [JSON:API](https://jsonapi.org/format/), as inspiration, not compliance. We use only the members we need, with JSON:API's meaning, and add others (`links`, `meta`, `relationships`, `included`, `detail`, `source`...) only when an endpoint has a real use for them.

- **Success** is a document with a top-level `data`: one resource object, or an array of them. A resource object has `type` (the kind of resource, a string, used consistently), `id` (a string; `type` plus `id` identify one resource), and `attributes` (its fields).

  ```json
  {"data": {"type": "health", "id": "api", "attributes": {"database": "ok"}}}
  ```

- **Failure** is a document with a top-level `errors` array, never alongside `data`. Each error object has:
  - `status`: the HTTP status, as a string.
  - `code`: an application-specific snake_case code a client can branch on.
  - `title`: a short summary that is the same for every occurrence.

  Nothing occurrence-specific goes in, so no internals can leak.

  ```json
  {"errors": [{"status": "503", "code": "database_unavailable", "title": "The database did not answer"}]}
  ```

  Routes build errors with `error_response(status, code=..., title=...)`; don't raise `HTTPException` with a `detail`, as the detail is dropped. FastAPI's own 404 and 405 (with its `Allow` header) and any unhandled exception (500) come out in this shape too; the 500's cause goes to the server log. Request validation errors (422) don't yet, because no endpoint takes input. The first one that does should convert them in `routes/errors.py`, using `detail` and `source`.
- **Services never return either shape.** They return plain results. The route is the only place that knows about `data`, `errors` and status codes.
- **Media type** stays `application/json`, not JSON:API's `application/vnd.api+json`. We don't follow the spec's content negotiation rules, and plain JSON is what curl, load balancers and generic clients expect.

The example is the health check. `HealthCheck.run()` (`services/health_check.py`) runs `SELECT 1` within 2 seconds, logs the cause of a failure, and returns `HealthOk` or `HealthUnavailable`. `GET /v1/health` (`routes/health.py`, mounted by `routes/v1.py`) converts them into the 200 and 503 documents above.

## Tests

| What you're proving | Where | How |
| --- | --- | --- |
| A rule in a pure function | `tests/unit/test_<module>.py` | Call it directly. No database, no app. |
| Every case of a service's logic | `tests/services/test_<service>.py` | Call its public methods and assert on the result it returns. The database is the real `api_test` (`database_url` fixture). For a database that is gone, silent or never answers, use the stand-ins in `tests/support/database_faults.py`. |
| A route is hooked up and converts each result | `tests/http/test_<resource>.py` | One case per outcome, through `api_client(database_url)` (`tests/support/api_client.py`): the whole app, the real service, the real database, nothing faked. Assert the status code and the exact document. Don't repeat the service's cases, and don't assert that the route called the service. |
| A response matches the OpenAPI document | Same | `assert_matches_documented_response` (`tests/support/openapi.py`), once per documented status. |
| App-wide error handling (404, 405, 500) | `tests/http/test_errors.py` | Same client. A behavior no real route triggers on demand gets a test-only route through `api_client(..., extra_routes=...)`. |
| The shipped image is wired up | `../e2e/api/tests/` | One test per journey, happy path only, against `api-release`. |

Tests are async (`pytestmark = pytest.mark.anyio`). A test that writes rows creates what it needs and is safe to run twice; the database is not reset between runs.
