# api

fortymm's HTTP API: FastAPI on Python 3.15, with PostgreSQL 18 (the `api-db` service). Run everything through `./bin/mise run api:<task>`; `CLAUDE.md` lists the tasks.

## Layout

| Where | What goes there |
| --- | --- |
| `src/api/services/<concern>.py` | A service class that holds one piece of logic, plus the plain results it returns (frozen dataclasses). It returns results for expected outcomes instead of raising, and knows nothing about HTTP or the response format: no status codes, no FastAPI types, no `data` or `errors`. |
| `src/api/routes/<resource>.py` | A route gets its service from `api.dependencies`, calls it, and converts each result into a status code and a response document (below). Its response models (`<Resource>Document`, `<Resource>Resource`, `<Resource>Attributes`) live in the same file. No logic of its own. |
| `src/api/routes/errors.py` | The error shape (`ErrorObject`, `ErrorDocument`), the shared errors (404, 405, 500), `documented()` and `error_response()` for routes, and the handlers that give FastAPI's own errors the same shape. |
| `src/api/routes/v1.py` | The `/v1` router. A new route module joins it with `router.include_router(...)` and writes its paths without the prefix. `/openapi.json` and `/docs` stay unversioned: one document covers every version. |
| `src/api/dependencies.py` | FastAPI dependencies that build services from settings (and, later, the connection pool). |
| `src/api/app.py` | `create_app()`: reads settings from the environment at startup (`src/api/settings.py`; `DATABASE_URL`), installs the error handlers and includes the routers. |
| `openapi.json` | The API's contract, generated by `api:openapi`. web-client's client types are generated from it (`web-client:api-types`), and `web-client:validate` fails until they are regenerated after a change. CI fails when it is out of date, and when it would break clients of the base branch's copy (`api:openapi-breaking`, oasdiff). Response models appear in it under their class names. Their docstrings become schema descriptions. |
| `Dockerfile` | The production image. The dev image is `dev/api/`. |
| `hosting/setup.sh` | The Google Cloud project the pull request previews run in, made by `api:hosting-setup` and checked by `api:hosting-check` ("Hosting", below). |

## Responses and errors

Response bodies are shaped after [JSON:API](https://jsonapi.org/format/), as inspiration, not compliance. We use only the members we need, with JSON:API's meaning, and add others (`links`, `meta`, `relationships`, `included`, `detail`, `source`...) only when an endpoint has a real use for them.

- **Success** is a document with a top-level `data`: one resource object, or an array of them. A resource object has `type` (the kind of resource, a string, used consistently), `id` (a string; `type` plus `id` identify one resource), and `attributes` (its fields).

  ```json
  {"data": {"type": "health", "id": "api", "attributes": {"database": "ok"}}}
  ```

- **Failure** is a document with a top-level `errors` array, never alongside `data`. Each error object has:
  - `status`: the HTTP status, as a string.
  - `code`: an application-specific snake_case code a client can branch on.
  - `title`: a short summary that is the same for every occurrence.

  Nothing occurrence-specific goes in, so no internals can leak.

  ```json
  {"errors": [{"status": "503", "code": "database_unavailable", "title": "The database did not answer"}]}
  ```

  **Each error is a typed class.** Subclass `ErrorObject` (`routes/errors.py`) and pin all three members to constants. An error a route owns sits in the route's file; a shared one sits in `routes/errors.py`.

  ```python
  class DatabaseUnavailableError(ErrorObject):
      status: Literal["503"] = "503"
      code: Literal["database_unavailable"] = "database_unavailable"
      title: Literal["The database did not answer"] = "The database did not answer"
  ```

  - **Declaring and sending:** a route declares an error with `responses=documented(DatabaseUnavailableError)` and sends it with `return error_response(DatabaseUnavailableError())`. Both go through the class's `DatabaseUnavailableErrorDocument`, so the OpenAPI document and the body can't drift apart. The document says the 503's `status` is `"503"` and its `code` is `"database_unavailable"`, and a generated client can narrow on `code`.
  - **`title` is a constant too:** JSON:API says it doesn't change between occurrences, and pinning it puts a change in the document's diff. If titles are ever localized, loosen it to a string then.
  - **Don't raise `HTTPException` with a `detail`:** the detail is dropped.
  - **FastAPI's own errors** come out in this shape too: 404 (`NotFoundError`), 405 (`MethodNotAllowedError`, with its `Allow` header) and any unhandled exception (`InternalServerError`, its cause in the server log). The `/v1` router documents the 500 on every operation, since any operation can raise. 404 and 405 are not documented: they are about paths and methods the document doesn't list.
  - **Request validation errors (422)** are not converted yet, because no endpoint takes input. The first one that does should convert them in `routes/errors.py`, using `detail` and `source`.
- **Services never return either shape.** They return plain results. The route is the only place that knows about `data`, `errors` and status codes.
- **Operation IDs** come from the route function's name (`operation_id()` in `app.py`): `get_health`. A new route gets one with no extra work. Name route functions verb_noun and keep them unique across the API; `api:openapi` and the tests fail on a duplicate.
- **Media type** stays `application/json`, not JSON:API's `application/vnd.api+json`. We don't follow the spec's content negotiation rules, and plain JSON is what curl, load balancers and generic clients expect.

The example is the health check. `HealthCheck.run()` (`services/health_check.py`) runs `SELECT 1` within 2 seconds, logs the cause of a failure, and returns `HealthOk` or `HealthUnavailable`. `GET /v1/health` (`routes/health.py`, mounted by `routes/v1.py`) converts them into the 200 and 503 documents above.

## Tests

| What you're proving | Where | How |
| --- | --- | --- |
| A rule in a pure function | `tests/unit/test_<module>.py` | Call it directly. No database, no app. |
| Every case of a service's logic | `tests/services/test_<service>.py` | Call its public methods and assert on the result it returns. The database is the real `api_test` (`database_url` fixture). For a database that is gone, silent or never answers, use the stand-ins in `tests/support/database_faults.py`. |
| A route is hooked up and converts each result | `tests/http/test_<resource>.py` | One case per outcome, through `api_client(database_url)` (`tests/support/api_client.py`): the whole app, the real service, the real database, nothing faked. Assert the status code and the exact document. Don't repeat the service's cases, and don't assert that the route called the service. |
| A response matches the OpenAPI document | Same | `assert_matches_documented_response` (`tests/support/openapi.py`), once per documented status. |
| App-wide error handling (404, 405, 500) | `tests/http/test_errors.py` | Same client. A behavior no real route triggers on demand gets a test-only route through `api_client(..., extra_routes=...)`. |
| The shipped image is wired up | `e2e/test_<journey>.py` | One test per journey, happy path only, against `api-release` (the production image) and its real database, over HTTP with the `api` fixture (`e2e/conftest.py`). Run by `api:e2e`, the last step of `api:validate`. |
| The hosting setup and check stop before touching Google Cloud without a login | `hosting/setup.sh` | `api:deploy-check`, the last step of `api:validate`. What the setup makes, and what the deployer may and may not do, is checked against the real project by `api:hosting-check`, which needs an owner's login and so isn't in CI. |
| The api and another app work together, or the hosting in front of the api | `../e2e/` | Only what can fail because of how the apps are served or connected; run by the stack-wide `e2e` task. |

`api:test` runs `tests/` only. Tests in `tests/` are async (`pytestmark = pytest.mark.anyio`). A test that writes rows creates what it needs and is safe to run twice; the database is not reset between runs.

## Hosting

Each pull request will get a preview of the api on Google Cloud: a Cloud Run service `fortymm-api-pr-<number>` with its own database `pr_<number>` on one shared Cloud SQL instance. This section is the project's foundation, made once by `api:hosting-setup`. The CI jobs that deploy and delete the previews come next ("What the preview jobs must do", below). Everything here is for previews only, and named so. A production api will get its own instance, role, secret and service accounts beside these. None of these grants reach them, except two of the deployer's, which Google Cloud can't narrow to the previews: its Cloud Run role and its databases role (below).

| What | Where |
| --- | --- |
| The setup, with every name in one block at its top | `hosting/setup.sh` |
| gcloud (and the Docker CLI, to push images), pinned | `../dev/api-hosting/Dockerfile`, the `api-hosting` service |
| The login | the `api-hosting-gcloud` Docker volume, never the checkout |

### Who may do what

**The deployer** (`api-preview-deployer`), what a workflow in `mightymoose/fortymm` becomes:

| Role | On | Why |
| --- | --- | --- |
| `roles/iam.workloadIdentityUser`, to `principalSet://.../workloadIdentityPools/github-actions/attribute.repository/mightymoose/fortymm` | the deployer itself | Lets that repository's workflows, and nothing else, become it. |
| `apiPreviewServices`: `run.services.create`, `.get`, `.update`, `.delete`, `.setIamPolicy` | the project | Deploy, redeploy and delete a preview service. `setIamPolicy` makes it public (`--no-invoker-iam-check`; the deploy is refused without it). A deploy, a redeploy and a delete work without `list`, `getIamPolicy` and `run.operations.get` (tried). **Not narrowed:** Cloud Run ignores an IAM condition on a service's name (tried: with one, even the names it allows were refused). So this holds for every Cloud Run service in the project, a future production one included. The preview tasks' name guards will keep it to `fortymm-api-pr-<number>`. |
| `apiPreviewDatabases`: `cloudsql.databases.create`, `.delete`, `.get`, `.list`, `cloudsql.instances.get` | the project | Create and drop a preview's database. Not the instance, its users or its settings. **Not narrowed:** Cloud SQL's database create and drop ignore an IAM condition on the instance's name (tried, with the instance's name and with names under it, after IAM had settled: always refused). So this holds on every instance in the project, a future production one included. A production instance in a project of its own would be out of its reach. |
| `roles/artifactregistry.repoAdmin` | the `fortymm-api-preview` repository only | Push, pull and delete images there. It can't delete the repository. |
| `roles/iam.serviceAccountUser` | `api-preview-runtime` only | Deploy services that run as the runtime account. |

It can't delete, change or create an instance, change database users, read the password, make keys or change the project's IAM. `api:hosting-check` asks Google Cloud so, as the deployer, every time it runs. Anyone who can deploy a preview can run code as the runtime account, and so reach the password and every preview database. The password opens nothing else.

**The runtime account** (`api-preview-runtime`), what the preview services run as:

| Role | On | Why |
| --- | --- | --- |
| `roles/cloudsql.client` | the project, only if `resource.service == 'sqladmin.googleapis.com' && resource.name.endsWith('/instances/fortymm-api-preview')`: the preview instance alone (an instance's name can't contain `/`) | Connect through Cloud Run's built-in Cloud SQL connection. ### Running it

Log in once, as an owner of the project, in a terminal (it prints a URL and asks for the code that page shows). Then run the setup and the check:

```sh
./bin/mise run api:gcloud -- auth login --no-launch-browser
./bin/mise run api:hosting-setup
./bin/mise run api:hosting-check
```

`api:hosting-setup` prints each item as `in place` or `created`, then the names CI needs. Creating the instance takes a few minutes. Run it again whenever you like:
- It creates only what is missing, and says `nothing to change` when everything is there.
- It never changes something that exists but differs (an instance of another tier, a role bound with another condition, a role too many). It reports `DIFFERS` and fails, and you decide.

`api:hosting-check` changes nothing. It fails on anything missing or wrong. It also asks Google Cloud, as the deployer, what the deployer may and may not do, and tries to read the password as the deployer, which must be refused.

Without a login, both stop first and say so. `api:deploy-check`, in `api:validate`, proves it.

### What the preview jobs must do

These are the steps step 2's tasks will take. They were tried by hand, as the deployer (impersonated), with the image built from this checkout's `api/Dockerfile`:

1. **Build for `linux/amd64`** (`docker build --platform linux/amd64 api`): Cloud Run runs amd64, and a Mac builds arm64 by default. After pull request #7, the build also needs `core/` as a second build context.
2. **Push** to `northamerica-northeast2-docker.pkg.dev/fortymm/fortymm-api-preview/api:pr-<number>`. The Docker CLI in `api-hosting` uses the host's Docker through its socket, after `gcloud auth print-access-token | docker login -u oauth2accesstoken --password-stdin https://northamerica-northeast2-docker.pkg.dev`.
3. **Create the database** if it doesn't exist: `gcloud sql databases create pr_<number> --instance=fortymm-api-preview`.
4. **Deploy:**

   ```sh
   gcloud run deploy fortymm-api-pr-<number> --region=northamerica-northeast2 \
     --image=<the image> --port=8000 \
     --service-account=api-preview-runtime@fortymm.iam.gserviceaccount.com \
     --add-cloudsql-instances=fortymm:northamerica-northeast2:fortymm-api-preview \
     --set-env-vars='^@^DATABASE_URL=postgresql:///pr_<number>?host=/cloudsql/fortymm:northamerica-northeast2:fortymm-api-preview&user=api_preview' \
     --set-secrets=PGPASSWORD=api-preview-database-password:latest \
     --no-invoker-iam-check --min-instances=0 --max-instances=1
   ```

   - `DATABASE_URL` names no host. The socket's directory goes in `host` and the user in `user`, since a URL can't have a user without a host. asyncpg takes the password from `PGPASSWORD`, so the address holds no secret. `src/api/settings.py` accepts this form.
   - `^@^` makes `@` the list separator, since the value holds `&` and `=`.
   - After pull request #7, the service also needs `ENVIRONMENT` (in `--set-env-vars`, e.g. `uat`).
5. **The address is known from the name:** `https://fortymm-api-pr-<number>-89514061125.northamerica-northeast2.run.app`, that is `https://<service>-<project number>.<region>.run.app`. The trial service got that address (Cloud Run lists it in the `run.googleapis.com/urls` annotation), beside an older random one (`status.url`, `https://<service>-<hash>-pd.a.run.app`). The Worker's proxy can rely on the first.
6. **Tear down in this order:**
   1. the service: `gcloud run services delete`;
   2. the database: `gcloud sql databases delete` (a database with open connections can't be dropped);
   3. the image: `gcloud artifacts docker images delete <image> --delete-tags`. That leaves the untagged manifests a Docker Desktop or OrbStack build pushes with it (the platform image and its attestation). The trial found two, and deleted them by digest (`gcloud artifacts docker images list <repository>`, then `delete <repository>/api@<digest>`). Building with `--provenance=false` should push a single manifest.

In CI, `google-github-actions/auth` gives gcloud the deployer's credentials. It needs `workload_identity_provider: projects/89514061125/locations/global/workloadIdentityPools/github-actions/providers/fortymm`, `service_account: api-preview-deployer@fortymm.iam.gserviceaccount.com`, and `permissions: id-token: write` on the job. The credentials must reach the `api-hosting` container: the credential file the action writes, through `CLOUDSDK_AUTH_CREDENTIAL_FILE_OVERRIDE`. The provider's condition above is what limits this to `mightymoose/fortymm`; the first preview run will be its first real proof.

### Removing everything

Do these in order, as an owner. Each command runs as `./bin/mise run api:gcloud -- <command> --project=fortymm`:

1. Every preview service: `run services list --region=northamerica-northeast2`, then `run services delete <name> --region=northamerica-northeast2` for each.
2. The instance, with every preview database in it: `sql instances patch fortymm-api-preview --no-deletion-protection`, then `sql instances delete fortymm-api-preview`. Its name can't be reused for about a week.
3. The secret: `secrets delete api-preview-database-password`.
4. The image repository: `artifacts repositories delete fortymm-api-preview --location=northamerica-northeast2`.
5. The bindings on the project, which would otherwise stay as `deleted:` members:
   - `projects remove-iam-policy-binding fortymm --member=serviceAccount:api-preview-deployer@fortymm.iam.gserviceaccount.com --role=projects/fortymm/roles/apiPreviewDatabases --all`
   - the same with `--role=projects/fortymm/roles/apiPreviewServices --all`
   - `projects remove-iam-policy-binding fortymm --member=serviceAccount:api-preview-runtime@fortymm.iam.gserviceaccount.com --role=roles/cloudsql.client --all`
6. The service accounts: `iam service-accounts delete api-preview-deployer@fortymm.iam.gserviceaccount.com`, and the same for `api-preview-runtime`. Their own bindings go with them.
7. The roles: `iam roles delete apiPreviewDatabases`, then `iam roles delete apiPreviewServices`. Their IDs stay taken for 7 days, and the setup undeletes them if it runs again within them.
8. The identity pool: `iam workload-identity-pools providers delete fortymm --workload-identity-pool=github-actions --location=global`, then `iam workload-identity-pools delete github-actions --location=global`. The pool's ID stays taken for 30 days, and the setup undeletes it if it runs again within them.

The APIs the setup enabled can stay; they cost nothing unused.
