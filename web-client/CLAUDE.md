# web-client

Vite + React + TypeScript. Runs only in Docker (see the root `CLAUDE.md`); never run `node` or `npm` on the host.

- Dev server: use the `web-client-dev` skill, or `./bin/mise run web-client:dev`.
- npm: `./bin/mise run web-client:npm -- <args>` (e.g. `install <pkg>`, `run build`, `run lint`).
- Source is in `src/`; the entry point is `src/main.tsx`.
- Unit tests: Vitest + Testing Library (jsdom). Tests sit next to the code under test as `*.test.tsx`, with a page object for each screen in `*.page.tsx` (`src/App.page.tsx` renders the whole app at a given path). Import `it` from `src/setupTests.ts` to get a `user` (userEvent) fixture. Test links by clicking through the whole app. `./bin/mise run web-client:test` runs them in the container.
- The Rust core: the `fortymm-core-wasm` package (wasm-bindgen, `--target web`), a `file:../core/bindings/wasm/pkg` dependency that the image builds from `core/`. In unit tests, load it with `initSync` and the `.wasm` bytes read from disk (see `src/core/core.test.ts`).
- Calling the api: `src/api/generated.ts` is typed fetch functions generated by orval from `api/openapi.json` (mounted read-only into the container). Never edit it: run `./bin/mise run web-client:api-client` after `api:openapi`, and commit both. Verify fails if it is stale. Wrap each call in a TanStack Query `queryOptions` next to the component that uses it, as `<name>-query.ts`, that checks the status and parses the body with a zod schema typed `satisfies z.ZodType<GeneratedType>` (see `src/components/health-query.ts`).
- Mocking the api in unit tests: MSW, started in `src/setupTests.ts`; requests with no handler fail. Handlers per endpoint are in `src/mocks/` (`ok` is the default; swap with `server.use(health.serverError())`), with faker for generated data. Render with `createTestQueryClient()` (no retries). Behaviour that needs a mocked api is tested here, never in e2e.
- Mocking the api on the dev server: while the web client is built ahead of the api, `src/mocks/dev-handlers.ts` lists the endpoints the api doesn't serve yet; every other request passes through to the real api. `src/main.tsx` starts it under `import.meta.env.DEV` (msw's Vite plugin, `msw/vite`, serves the worker), so a build has none of it. Each dev handler is temporary: delete it once the api serves that endpoint.
- E2E tests: Playwright, in `e2e/`. They run against a production build and the real api, never the dev server or mocks: add a page's e2e spec once the api serves what it needs. `./bin/mise run web-client:e2e` runs them in the container (Chromium is baked into the image; Playwright builds the app to `/tmp` and serves it with `vite preview`, which proxies `/api` to the api); verify runs them against `web-client-nginx`. The HTML report goes to `playwright-report/`. Page objects the whole-stack journeys (`/journeys`) drive are exported from `e2e/pages.ts`.
- Offline: `vite-plugin-pwa` (in `vite.config.ts`) generates a Workbox service worker in `vite build` only, never on the dev server. It precaches the whole build and serves `index.html` for every route except `/api`, which always goes to the network. Registration is `prompt`: a new build's worker waits, and `src/components/AppUpdate.tsx` shows a toast whose Reload switches to it (it also checks for a new build hourly). Unit tests mock `virtual:pwa-register/react` in `src/setupTests.ts`. nginx serves that build (`nginx.conf.template`, `/api` proxied to `$API_URL`) as `web-client-nginx` (started by dev) and as preview. Test offline behaviour in the journeys (`/journeys`), which run against `web-client-nginx`; the e2e tests here run on a build too, so the Workbox worker is registered in them.
- Design system screenshot tests (`e2e/design-system/`): every spec runs against both the reference boards and the app, and both compare to the same committed screenshots in `e2e/design-system/__screenshots__/`. Baselines come only from the reference: `./bin/mise run web-client:screenshots`, never `--update-snapshots` on the app. Comparison is pixel-exact (`threshold: 0`), so the app must match the board's layout down to subpixel positions, not just the piece under test. `src/design-system/` is a copy of the reference's `ds/fortymm/` (tokens, self-hosted fonts, `kit.css`).
